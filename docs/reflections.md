# Reflections
## Dependency Graph
The final dependency graph can be found in `docs/dependency_graph.svg`. We created others, but decided to include only this one because it was the most useful during the migration process. The graph reveals an implementation order for the methods in `app.py` in the legacy application. It suggests that the least painful approach would be to start on the left and move to the right as the earlier methods are completed. This order helps avoid friction because methods with the fewest dependencies are implemented first. That way, the person implementing them does not block the others, and the others do not have to wait for the implementer. Conversely, the nodes on the right show that it might be a good idea to set up a database as early as possible, so that parallel work can begin sooner and we can increase our efficiency and use of capacity. This is exactly how the process unfolded among us. It should be noted, however, that we did not actually create this graph before starting the work; apparently, we had each formed an internal version of it by reading the legacy code.
 
## Problems with the Codebase
A ranked list of problems is compiled in `docs/legacy_problems.docx`. It is ranked primarily by the consequences for users. Without users’ trust and satisfaction, the search engine will never gain widespread adoption, and we will lose our jobs. This is reflected in the list: Security issues rank highest, followed by a missing test for core functionality. Without a working, falsifiable test, no one can be sure that the search functionality actually works. That functionality is the foundation of our existence. A lack of security will scare users away as soon as it is exploited. Hence the ranking. After that come less serious issues, such as confusing naming, which is hidden from customers but can make future work more difficult for us and our colleagues, or styling.
 
## OpenAPI Specification
The specification can be found in `docs/swagger.json` (or `.yaml`, if you prefer).
 
Wherever possible and appropriate, we have shaped endpoint responses, response data structures, and status codes to match the legacy application’s OpenAPI specification. In some cases, however, we have extended it in our own specification. In `APISearch()` in `internal/handlers/search.go`, for example, the attentive reader will notice that status code `500` has been added alongside the expected `200` and `422` status codes. We return it for errors that are either not handled or not explicitly handled in the legacy application—for example, when a response fails to be converted to JSON. We have also updated parameter descriptions and success and error status-code descriptions in several places to clarify when errors occur and exactly what is returned in response to requests. This helps downstream customers implement extensions or use our API more effectively.
 
The specification was generated with `swaggo`, a tool that semi-automatically generates documentation based on annotations and tagged structs used in the annotations when they describe responses. It has worked well so far, although it has frequently caused merge conflicts. However, the tool’s reliance on annotations requires us to be very disciplined about keeping them in sync with the code. This is necessary because generating documentation this way risks the code’s actual functionality and its documentation drifting apart over time. A tool which generated documentation exclusively from the code would be ideal: It would prevent this problem, make the documentation process easier, and save quite a few lines of code. Moreover, with such a tool, we could avoid having to remember a lot of annotations and their formats. This is not a major problem given the internet and good documentation, but an ideal tool of this kind could eliminate that cognitive burden. We have yet to find such a tool.
 
## Branching Strategy
See our decision-making process in pull request #97 and `docs/choices-and-challenges.md` (near the bottom, under “choices,” beneath the heading “05/10/2026”), and possibly also `docs/branching-strategy.md`. The outcome of the debate was that we use GitHub Flow: a process with one long-lived branch (`main`) that can be deployed continuously. Short-lived branches are used temporarily to develop features, write documentation, and carry out refactoring. When these are finished, a pull request is opened for others to review. Once reviewers have approved the changes (and CI checks allow it), they are merged into `main`. To support this, we have developed a set of requirements: the review process (see `docs/choices-and-challenges.md` under “choices” in the table dated 08/09/2026), our pull request template (`.github/pull_request_template.md`), and automated CI checks (a linter and tests run sequentially, with the tests naturally depending on the program being buildable—see `.github/workflows/*.yml`). We also use Git hooks and automatic linting for local quality control before changes can be committed or pushed to `origin` (see `hooks/`). After a PR is merged, the branch is deleted, and the process is repeated with a new task. The reason for this strict CI and QA setup is precisely to ensure that `main` can be deployed at any time.
 
We chose GitHub Flow because it allowed maximum flexibility in parallelizing work, given our mismatched working hours and small team size. This explains why we did not choose trunk-based development, which requires synchronous work. With only one branch and our mismatched schedules, there would be a lot of wasted time waiting for other people’s changes, although there would probably be fewer merge conflicts. We have not yet experienced any time-consuming or destructive merge conflicts, however.
 
We ruled out Git Flow because we have not yet needed multiple long-lived branches, and the overhead and cognitive load they entail have not yet proved worth the cost in our context. We also had in mind that we would need to implement CD, which is cumbersome with Git Flow because deployment and testing are out of sync: the code remains on the `release` branch until it is integrated after testing is complete. Instead, we test each feature immediately, so that future testing and CD are made as straightforward as possible. This does, however, require the process steps described in the first paragraph above, still under “Branching Strategy.”
 
The final candidate we considered was GitLab Flow, which is very similar to GitHub Flow and includes many of the same practices. We did not choose GitLab Flow because we have yet to need the additional flexibility it offers for release management and separate release and environment branches. We may very well need that in the future once we start looking at deploying releases or if we need to ship different versions simultaneously.
