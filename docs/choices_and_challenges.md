| 08/09/2026        | We have chosen the following coding conventions and will enforce them automatically in the CI/CD pipeline using `revive` and its associated GitHub Action: * Branches are named using the format `[branchGroup]/branch-name`. Typical groups would be `feature`, `hotfix`, ... * The directory structure generally follows the Go project layout: a project in the root directory with subdirectories for specific functionality:     * `/cmd` for files that contribute to executable files. Each subdirectory here should have the same name as the executable file it exposes.     * `/internal` for files used only internally—private libraries, in other words, files that should not be used by downstream clients.     * `/api` for files related to endpoints, such as the OpenAPI specification (also found in `/docs`).     * `/pkg` for files that can be used by downstream clients.     * `/web` for static assets (such as images, markup, and styling) for the site.     * `/test` for tests. * Names may not be abbreviated (`context` can't become `ctx`). We use `error` instead of `err`. * Variable names may not contain type names. * Exported variables are named in PascalCase, private ones in camelCase. The same is true of method names. * Struct names are written in PascalCase. * Indexes in loops have usual names: `i`, `j` and `k`, ... * booleans start with "is", "has" or "should", followed by a verb, noun or adjective. * "id" is written with both letters capitalized: `ID`. * Prefer code over comments, but document code in docstring equivalent comments exactly above what it documents.                                 | We wish to have and enforce code conventions, so that PRs violating these cannot be merged before they're corrected.                                                                                                                                                                                                                                                                                                                                                                                 | Plenary discussion following brainstorming, during which each group member proposed an idea, followed by synthesis (in person and digitally). |

| 08/09/2026        | At least one other person than the one requesting must review a PR. You may merge your own branch after a successfully completed review. A reviewer should do the following: 1. Read the description, related issue, and high-level diff. Determine:     1. What problem is being solved?     2. Is the approach appropriate (too slow/uses too much memory/bandwidth)?     3. Does the implementation match the requirements?     4. Are important edge cases or affected components missing? 2. Review correctness     1. Correct behavior on normal and exceptional paths      2. Boundary conditions and invalid input (nil, messed up structs, ...)     3. Error handling (is it centralized appropriately, are all potential error states covered?)     4. Data validation (input from forms and the like)     5. Database transactions (are transactions used when appropriate?) 3. Maintainability     1. Does the code conventions linter warn on their code?     2. Is the code understandable?     3. Are names precise and fitting?     4. Is the design consistent with the existing system?     5. Is complexity justified? Can anything be simplified?     6. Is duplication avoided without creating unnecessary abstraction?     7. Are comments explaining intent rather than restating the code? (if so, good)     8. Will another developer be able to modify this safely later? 4. Tests     1. Cover the primary behavior     2. Cover failure and edge cases     3. Are readable and deterministic     4. Test behavior rather than implementation details (uses mocking in unit tests, for example)     5. Would fail if the feature were broken | We want external verification of code to heighten quality. Peer review is a great way to get there in concert with the automated methods we will employ.                                                                                                                                                                                                                                                                                                                                             | Plenary discussion (in person).                                                                                                               |
